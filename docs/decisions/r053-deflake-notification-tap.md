# r053-deflake-notification-tap

Short form. Goal: testNotificationTapOpensRelease passes on a fresh simulator the first time, so a red run means a real N-6 break (v0.5.3 tag blocker).
Smaller alternative: a longer wait for the Open button (rejected: the button was found, then gone). Do nothing: not allowed, a flaky gate hides real failures.
Cause (from the failure text, not reproduced here): "No matches for 'Open' in swipe-action-button-identifier" at 7161347. The button existed when found and was gone when `.tap()` resolved it a second time. A first row tap that does bring the app up also hides the slide-out. The first run on a fresh sim failed after 132 s; the second passed.
Decision: tapOpenIfRevealed stops as soon as the app is in front, reads the button from one snapshot (which throws, not fails, when it is gone), and taps that point on SpringBoard. Test-only; no app code changes.
Weighed in: Quinn signs.
Learning: never resolve a SpringBoard element twice; read its frame once and tap the point.

Update (c4d2fae failed twice on a fresh sim on the Mac): the failure moved earlier, to "no banner and no row after 3 pulls; app says: qa-schedule: none". That "none" was not evidence: the test relaunched the app after the cold terminate, so it read a new process's empty log. Two changes. The app's QA schedule log now also reports the notification authorization status ("auth 2" = authorized; INTERNAL builds only). The test keeps accepting the permission prompt for up to 30 s until the app reports a status, stops with a plain message when it is denied, and on the cold failure path reports the log it read before the terminate. If a fresh-sim run now fails, the message says whether permission, scheduling or delivery is the broken step.
Learning: a probe that restarts the thing it probes proves nothing; read the state before you end the process.

Update 2 (f526773, two fresh-sim runs, Mac screen locked): run 2 scheduled with permission granted ("auth 2; added") but no row appeared after 3 pulls, which is a delivery question the locked screen may explain; the deciding test is a rerun on an unlocked screen. Run 1 showed `qa-schedule: none` for 40 s: the `simulate` route awaited the permission request, no prompt was presented, and nothing was scheduled. Fix (INTERNAL QA route only): ask for permission, wait up to 8 s for an answer, then schedule anyway; a pending request is delivered once permission is granted, and the test reports the status. Not claimed: that this fixes run 2.

Update 3 (Quinn, 4c39193, fresh erased sim, Closed: run 1 failed, run 2 passed; the log read "adding, due in 3 s" and never "added", with no "auth" segment): `added` and `auth N` both come from notification-daemon completion handlers, so neither firing means usernoted did not answer. That is the simulator, not the app. The test now fails with its own message ("the notification daemon did not complete add() within 10 s ... reboot or erase the simulator") after waiting 10 s for `; added`, instead of surfacing minutes later as "no row". Nothing loosened: the cold row and the "simulated" release page stay required. Gate evidence is two passes in a row on a sim whose permission is already granted; a fresh-sim run that needs a second try is not green.
Learning: a completion that never fires is a different failure from a missing result; name it where it happens.

Update 4 (Mac, 4c39193 run 1): the permission alert (Allow / Don't Allow) was still on screen at the end; the permission loop ran its 30 s and never tapped it. `springboard.alerts.buttons[...]` did not find it. The loop now looks for the allow button in SpringBoard alerts, any SpringBoard button with an allow label, and the app's own alerts, and logs which it tapped. If the app still has no auth status after 30 s the test stops with its own message and attaches the SpringBoard hierarchy and a screenshot, instead of waiting minutes for a notification that cannot arrive. Not claimed: that these queries find the alert; the attachment will say if they do not.
Learning: when a prompt is on screen and the code looked for it in one place, search every place and dump the tree on a miss.
